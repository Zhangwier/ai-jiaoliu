              09　Transformer：注意力按相关性组合上下文信息

              来源：S33；注意力权重为示意 来源索引 ›

              • https://arxiv.org/abs/1706.03762
              原稿备注与补充口径
              讲解与会后阅读

“把图纸和清单放在一起，检查它是否与图示一致。”

模型需要结合周围文字，判断“它”指的是清单、数量还是某个尺寸。注意力机制帮助不同位置的信息相互关联。

训练时：从大量样本学习这些关联。

使用时：当前输入和对话为生成提供上下文。

边界：能关联远处信息，不代表必然准确找到每个细节，长文档仍需要定位与核验。

S33 Transformer 原论文

补充讲解：
读到“它”时，模型会给句子里每个词算一个相关度，再按相关度把这些词的信息加权混进来。图里线越粗，表示权重越高（数字为示意）。
Transformer 的三个特点：① 所有词同时处理，适合用 GPU 并行训练；② 相隔很远的词也能直接建立关联；③ 这样的注意力层叠几十上百层。
这也埋下了“上下文腐烂”的伏笔：上下文越长，要分配注意力的词越多，关键信息更容易被稀释。

              12　抽卡：同一个问题，两次回答可能不同

              来源：Thinking Machines（2025-09-10）；本地鹈鹕测试

              • https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/
              原稿备注与补充口径
              讲解与会后阅读

抽卡（同一句话，不同质量的结果）

根源：上一页的生成过程。温度大于 0 时，每一步按概率抽 token；某一步抽到不同的词，后面整段都会走上另一条路。

就算把温度设成 0，在线服务也不保证每次一样。Thinking Machines 的实验：Qwen3-235B，同一句“Tell me about Richard Feynman”，温度 0，跑 1000 次，得到 80 种不同回答；前 102 个 token 完全一样，第 103 个开始分叉（992 次写“Queens, New York”，8 次写“New York City”）。主要原因是服务器负载变化导致批次大小变化，计算结果出现微小差异。

工作中的含义：一次结果好不代表每次都好，一次结果差也不代表模型不行。重要任务多跑几次比较；关键结论不靠单次输出。

后面的鹈鹕测试，每个配置也只跑了一次，所以只能说明“这一次”的表现。

幻觉

根源：模型每一步只挑“最像”的下一个 token，不会停下来查证。材料里没有答案时，它倾向于补一个看起来合理的答案。

迎合（谄媚）

根源：训练第三步按“人喜不喜欢”给回答打分。人往往更喜欢被认同，于是模型学到了“顺着说”。

真实事件：2025-04-29，OpenAI 回滚了一次 GPT-4o 更新。官方说法：这次更新让模型“overly flattering or agreeable—often described as sycophantic”（过度奉承、附和），原因是“focused too much on short-term feedback”（过于看重短期反馈）。

研究：Anthropic 的论文《Towards Understanding Sycophancy in Language Models》测试了 5 个当时最先进的 AI 助手，在 4 类任务中都稳定出现讨好行为；而且相当一部分时候，人和偏好模型都更喜欢写得漂亮的讨好回答，而不是正确回答。

工作里的表现：你问“这里是不是有错”，它倾向于找出一个错；你说“我觉得没问题”，它倾向于同意。

对策：开放提问，“请判断是否存在问题，没问题也可以”；要求它同时给出反例或反方证据。

              16　长上下文：输入长度和位置会影响信息利用

              来源：Chroma Research《Context Rot》（2025-07-14）；Liu 等，arXiv 2307.03172

              • https://arxiv.org/abs/2307.03172
              • https://research.trychroma.com/context-rot
              • https://www.trychroma.com/research/context-rot

              讲解与会后阅读

上下文腐烂

根源：注意力机制要给上下文里的每个 token 分配权重。内容越多，关键信息分到的越少，干扰越多。

研究 1：Chroma《Context Rot》（2025-07-14）测了 18 个模型（含 GPT-4.1、Claude 4、Gemini 2.5、Qwen3 等），结论是“输入越长，表现越不可靠”。LongMemEval 测试里，只给相关的约 300 token，明显好于给完整的约 113k token；加一个干扰句就会降分，干扰句越多降得越多。左图是其中“重复词”任务：横轴是输入长度，纵轴是得分，几个模型都随长度下降。

研究 2：Lost in the Middle（Liu 等，2023）：关键信息放在开头或结尾时最好找，放在长上下文中间时明显变差。

和“上下文窗口”不是一回事：窗口 1M 只说明装得下，不代表都用得好。

对策：一个任务一段对话，聊久了就新开；只给相关材料；关键要求放在开头，必要时结尾再重复一次；长文档先让它定位、再回答。

多模态（视觉）和 OCR 的区别

多模态模型可以直接“看”图片，能看到线条、标注和它们的位置关系。OCR 只是把图上的字识别出来变成文字，图形、尺寸线、标注对应哪一段，这些信息基本都丢了。

图纸 K1、K2 都要把“大样图上的标注”和“引线上的公式”逐段对照，只拿到文字是对不上的。

各配置的自述：
Opus：“原图为扫描件，数据经人工识读”（原图其实是矢量 PDF，这句说错了，但它确实看了图）→ K1、K2 都命中。
GPT：“OCR 仅辅助定位；参数、60 条钢筋记录、页下注均回看原图”→ 命中 K1。
Qwen：“文字提取无效，我按 A4 横向 3～14 倍渲染成图后逐格读表”→ 命中 K2。
GLM：“高清矢量化渲染 + 逐格放大读图”，用时 1 小时 24 分，结论“未发现实质性错误”→ 看得见也不一定看得出。
Seed：“通过 OCR 识别图纸内容”→ 0 命中；假错误全是 OCR 伪影，比如把人名识别成“陈d喜”、把表头“β(°)”识别成“β()”。
HY4：“不支持视觉/图像内容理解——我无法“看”这张图纸”，只分析了 PDF 元数据 → 0 命中。这是本次环境配置，不能推广为模型本身不支持视觉。
WorkBuddy Auto fast、MiniMax、Step 5 没说明读图方式；DeepSeek 只说“图面识读”。

结论：能看图是必要条件，不是充分条件。用工具前先确认：图片到底有没有进到模型的输入里。

                                                40　三类活：越需要人判断，检查越要加码
                                                  原稿备注与补充口径
                                                  讲解与会后阅读

什么样的活，适合交给 AI

这一页不列清单，列判据。前面举过的那些活只是恰好符合下面几条；换一份工作、换一个项目，照样用这五条去筛。

1. 格式是死的。章节、表格列、单元格位置都事先定好，它只负责往里填。要不要改结构、该分几章，仍然是人的判断——这部分交给它，往往就发散。

2. 答案唯一。同一份材料，不同人做出来应该是一个数。凡是"看情况""要商量"的判断，交给它只会得到一个看起来很确定的错答案。

3. 对错能当场验。合计对不对、条目少没少、位置对不对，打开文件就能看出来。验证成本低于重做成本，这类活才值得交出去。

4. 依据在材料里。答案写在给它的文件上，它只负责找出来、搬过去。不能靠它"知道"——它不知道的时候也会往下写。

5. 重复到人会烦。几百个文件里找一份、上百条子目逐条核对，机械重复、量大，人做容易漏也容易烦；这类活它不累。

用法：五条全中，直接交；中三四条，交出去但加强核对；只中一两条，自己干更快。

注意分寸：这五条讲的是"这活适不适合"，不是"这个模型行不行"。模型强弱决定它做得多细，判据决定该不该交给它。

依据：本人日常任务记录（2026）。

                                                  41　第一类实例：百余个文件中定位一张图纸
                                                  来源：本地文件索引脚本与生成结果（2026-10）
来源索引 ›
                                                    原稿备注与补充口径
                                                    讲解与会后阅读

拿"找图纸"举例：先建索引，再检索

1. 痛点：一个标段一百多个图纸和数量表文件，散在十几个分册目录里。找一张数量表，要么翻目录文件，要么按文件名猜，实际常常要花十几分钟。

2. 做法：先扫一遍根目录，生成一张索引表。表里九列：序号、文件名、类型、出图编号、所在册/分册、子目录、大小、修改时间、相对路径。备份文件和临时文件跳过；出图编号来自各册目录，目录没提供的就留空。

3. 另一张「册汇总」：按册统计文件数、体量、各类文件各几个。先看它能判断该翻哪一册，不用一个个点开。

4. 用法：按册筛、按出图编号定位、按类型找同类。表里没收录的，直接问它——它会去翻目录和分册表，再告诉你大概在哪一本。

5. 这就是最简单的 RAG 思路：先把资料整理成可检索的结构，再让模型在命中的片段上回答，而不是把整个文件夹塞进去。区别在于这里检索的是文件名和出图编号，不是向量。

6. 可复现：换项目只改一个根目录参数重跑脚本。这也是它的价值——索引能重生成、能核对，不是一次性的死表。

上下文管理的几个做法

1. 一个任务一段对话：换任务就新开，避免前一个任务的材料干扰。
2. 长了就压缩：多数编程客户端有“压缩/总结上下文”的功能（例如 Claude Code 的 /compact），把前面的过程总结成要点后继续；或者让它写一份进度摘要，新开对话贴进去。

                                                          46　RAG：让模型从“闭卷考试”改成“开卷考试”
                                                          来源：Chroma《Context Rot》；Lewis 等 RAG 原论文（2020）；火山引擎开发者社区《RAG 提示工程（一）》；吴恩达 RAG 课程（B 站 BV1KFb6z2EFE）
来源索引 ›
                                                            原稿备注与补充口径
                                                            讲解与会后阅读

这一页从零讲 RAG，先给比喻，再给流程。

比喻：普通大模型是闭卷考试，只能凭训练时记住的东西答；遇到没见过的（新规范、单位内部文件），它不会交白卷，会按“最像”编一个。RAG 是开卷考试：答题前先翻书，把相关的几页找出来，照着书答，还能告诉你抄的是哪一页。

名字拆开：R 检索（翻书找段落）＋ A 增强（把找到的段落贴进提示词）＋ G 生成（模型照着写）。注意它不改模型参数，资料更新了，重建一次索引就行。

流程分两段：
考前（只做一次）：把资料切成几百字一段，每段用 embedding 模型变成一串数字（向量），存进向量库。意思相近的段落，数字也相近。
考时（每次提问）：问题也变成一串数字，到库里找最接近的 3–5 段，把段落和问题一起交给模型，要求它只依据这些段落回答、标出处。

为什么值得这么麻烦：一是少编（原文在眼前，有东西可抄、能标出处；再加一句“只依据片段回答，找不到就说没找到”）；二是省 token：100 页中文资料约 5–8 万 token，整包塞进去每问一次付一次，检索只送命中的 3–5 段（一两千 token），差几十倍（按原稿口径估算）。

                                                            来源：Boris Cherny（Claude Code 负责人）X 帖，2026-02-01；Lewis 等 RAG 原论文（2020）；Claude Code 官方文档（Glob / Grep / Read 工具）

常被问：现在 Agent 自己会翻文件夹，文件夹里还有目录索引，还要 RAG 干什么？

区别在“索引到哪一层”和“靠什么找”。
一，目录索引是文件一级的：它告诉 Agent “合同在 03 文件夹第 2 份”，Agent 打开后还是整份（或整页）读进来，读进来的都算 token；RAG 是段落一级的，库里每几百字一段都有一个“意思坐标”，直接递上最相关的 3–5 段。
二，翻文件夹靠线索：文件名、目录、关键词搜索（grep）。字面一个字不重合就漏，比如问“防撞设施”，规范里写的是“挡块”。RAG 按意思找，能落到那段。
三，翻文件夹是多轮的：列目录、打开、读、发现不对再找；RAG 一轮取回。
四，反过来，翻文件夹的好处是永远是最新的，不用维护；RAG 资料一改就要重建索引，不然查到旧版。

真实例子：Claude Code 负责人 Boris Cherny 2026-02-01 在 X 上说，早期版本用过 RAG＋本地向量库，后来发现 Agent 自己搜索（glob、grep、读文件）总体更好，也更简单，没有安全、隐私、索引过期和可靠性这些问题。注意那是写代码的场景：代码文件名清楚、术语固定、要顺着引用读全文。规范库、历年报告这种“资料多、说法杂、反复问”的场景，RAG 仍然划算。

怎么选：几十份、名字清楚，让它翻文件夹；成百上千页、换说法多，上 RAG；很多产品两样都给，把 RAG 做成 Agent 的一个搜索工具。
                                                              

                                                              48　工作流例一：审一张图纸，五步各有人、有标准、有产物
                                                              来源：本稿图纸审查与修编报告两个案例的实际执行与复核记录；表格结构说明
来源索引 ›

前面讲了 RAG 只解决“找得到”。这一页回答：找到之后，怎么保证“读得准、摆得对、算得出”。办法不是换更强的模型，是把一件事拆成步骤，每步写清标准和产出。

左边是审图的五步，注意第三列——那是这一步“算不算做完”的判据，不是操作说明：
① 定范围：几页、哪些表，图纸是“看图”还是“只 OCR”，先问清；
② 提取：OCR 与视觉识别，标准是页数、表名、行数对得上，缺页要报出来；
③ 逐项核对：拿图纸和图例、数量表互对，标准是每条结论都有位置和原文；
④ 复算：关键工程量自己算一遍，标准是能独立复算；
⑤ 汇总结论：分“明确不一致 / 待确认 / 未检查”，标准是不许把待确认写成已确认。

右边做修编报告，同样的骨架：读清单、定位变更、套模板、复算、写原因。两个案例里踩的坑——单位 mm/cm 被当成错误、112 元差额、透水管核减 71.8663 万元——全都能归到某一步的“标准没定死”上。

最下面那条最关键：工作流不是一次画完的。每跑一次，把踩到的坑写成一条标准，这就是“不断总结”，也是这套东西真正变成资产的地方。

这一页补的是“优缺点与适用条件”，不是“怎么搭”。

先说真实收益，两条：并行——三个 Agent 各查一份清单的不同章节，原来串行四十分钟的活十几分钟能出初稿；上下文隔离——每个 Agent 只看自己那一摊，主线上下文不被几十页材料冲淡，这正好接前面讲的上下文腐烂。

再说代价，三条，而且都真实发生过：成本翻倍（三个 Agent 就是三份 token）；写冲突（两个 Agent 改同一个文件，后写的把前面的覆盖掉）；最要命的是同一个错误前提——三个都用了错的汇总口径，就会一起错，而且看起来像“三方交叉验证过”，比一个 Agent 错得更可信。

适用条件四个，缺一就别拆：任务能切成互不依赖的块、每块有独立可查的产出、写作用范围不重叠、有人负责合并与验收。

什么时候别拆：步骤前后强依赖（第二步要用第一步的结论）、总量本来就小（拆完协调成本比干活还多）、没有验收人。

结论那句要讲透：人多不自动变可靠。复核的人如果只是复述执行者的答案，那等于没复核——必须回到原材料。
                                                                        

                                                                        53　工作流与 Agent 编排的三个陷阱，本稿都踩过
                                                                        来源：本稿两案例的执行与返工记录；多 Agent 协作记录；本稿整理
来源索引 ›

这一页是全稿里最“反自己”的一页：前面花了很大力气讲工作流和多 Agent，这里要说清它们什么时候会害人。三条都是本稿真实踩过的，不是转述别人的说法。

第一条：低级模型加一堆工作流，不如高级模型一句话。
原因是：工作流不会增加模型的理解力。它只是把任务切小、把要求写细。如果模型本来就听不懂“这一步到底要什么”，切成五步只是把同一个误解重复五遍，而且每一步都多一次出错机会。实测里最典型的是图纸审查：配置差的那几组，不是步骤不够细，是根本没看懂图。反过来，Opus 那一档一句话下去，两个关键检查点（K1、K2）全中——它不需要被拆成五步。
所以顺序应该是：先确认模型够不够用，再谈工作流。模型不够，工作流只能让你更快地得到错的东西。

第二条：工作流如果不逐步人为确认，很容易花大量时间产出一堆垃圾，而且事后看不出是哪一步坏的。
这条我体会最深。一条五步流水线跑完，交出来的东西不对，你想回头查：是第一步材料读错了？第二步切分切坏了？还是第三步判断偏了？中间产物没留，就查不出来。于是只能整条重跑，时间全耗在重跑上。
所以工作流的第一个设计原则不是“自动”，是“每步留一个能查的产物”。这也是我不喜欢“Agent 编排”的原因：编排把步骤藏在黑箱里，中间态不落地，出问题只能靠猜。

第三条：低级 AI 理解不了你的意思，换另一个 AI 来看也理解不了。
很多人以为“让另一个模型复核”能救。但如果复核者拿到的还是同一段模糊描述，它只会给出另一个同样模糊的判断——两个都不懂，加起来还是不懂。复核能起作用的前提是：被复核的东西本身有据可查（原文、页码、算式），复核者能回到材料上逐条对。否则“两个模型都说对”只是两次猜测。

三条合起来是一句话：模型的理解力是地基，工作流是脚手架。地基不够，脚手架搭得再漂亮也没用。

屏幕精简前的完整文字：坑一低级模型 ＋ 一堆工作流 ＜ 高级模型一句话工作流不增加理解力，只把同一个误解重复五遍，还多四次出错机会。本次观察：差的那几组不是步骤不够细，是没看懂图；Opus 一句话，两个检查点全中。怎么避先确认模型够不够用，再谈工作流坑二不逐步确认，跑完一堆垃圾，还查不出哪步坏的五步跑完结果不对，中间产物没留，就只能整条重跑。时间全耗在重跑，而不是定位。怎么避每步必须留一个能查的产物——这也是“不喜欢 Agent 编排”的根源坑三这个 AI 听不懂，换另一个 AI 看也听不懂复核者拿到的还是同一段模糊描述，只会给出另一个同样模糊的判断。两个都不懂，加起来还是不懂。怎么避复核的前提是：材料本身有据可查，能回到原文逐条对顺序不能反：先确认模型够不够用，再决定要不要拆步骤、拆几个 Agent

术语速查 A1

Token（词元）：模型读写文字的最小单位，计费和上下文都按它算。汉字和 token 不一一对应，按各家分词器算。

上下文工程：决定把哪些资料、历史、规则放进上下文。比反复改提示词更影响结果。
RAG（检索增强）：先从资料库检出相关片段，再让模型作答。检索漏了，回答就漏。
Embedding（向量）：把文字变成一串数字，用来算“意思相近”。知识库检索的底层。
API / API Key：程序调用模型的接口；Key 是计费凭证。Key 泄露＝别人花你的钱。
按量 vs 订阅：API 按 token 付费；订阅按月给额度。积分 / Credits 是客户端自己的计量单位。
缓存命中：重复的前文不重复计费或打折。长对话前文保持不变更省钱。
限流（429）：每分钟、每天能调用的次数或 token 上限。报 429 就是触发限流，等一会儿再试。

这一页回答“DeepSeek 的开源到底彻底在哪”，也是听众最容易被“开源”两个字糊弄的地方。

先拆成四层，从浅到深：
一，权重开放。把模型参数放出来，能下载、能自己跑。多数“开源模型”只做到这一层。
二，许可宽松。DeepSeek 的做法是代码用 MIT、模型用自建许可（基于 OpenRAIL 修改）。官方 FAQ 明确：可商用、免费、无需申请登记；衍生模型不必开源（不是 GPL 那种传染式），但要保留版权声明、显著声明修改、遵守用途限制。作为对比，Meta 的 Llama 用的是自家社区许可，限制更多（比如月活到一定规模要额外申请）。
三，训练细节公开。V3 技术报告公开发表（671B 总参数 / 37B 激活），包含架构、训练策略和成本说明。这是“能被复现研究”的关键一层。
四，底层算子与工具开源。2025 年 2 月 24 至 28 日的“开源周”，连续放了五个库：FlashMLA（Hopper 上的 MLA 解码内核）、DeepEP（MoE 训练推理的 EP 通信库）、DeepGEMM（矩阵乘算子库）、EPLB 与 DualPipe（负载均衡与流水并行）、3FS（Fire-Flyer 文件系统）。这些是“怎么把硬件榨干”的东西，通常厂商不外传。

为什么第四层最能说明态度：前三层给你“结果”，第四层给你“方法”。愿意公开方法，等于承认别人可以照着做得更便宜。

关于“国产追上”的时间点要说准：DeepSeek 第一代是 2023 年的 DeepSeek-LLM 与 DeepSeek-Coder；真正让国产大模型被全球认真对待的是 2024 年底的 V3 与 2025 年初的 R1。所以讲“转折点”要落在 V3/R1 这一波，不要说成 V1。

提示词大意（讲的时候念一遍就够）：
“画一张孙悟空驾驶的飞机（机身写‘筋斗云 WUKONG AIR’），飞机上有一辆自行车，一只鹈鹕骑着自行车，鹈鹕背上驮着秦始皇，秦始皇骑着一只北极熊，秦始皇手里拿着螺丝刀在打螺丝，鹈鹕嘴里冒出气泡，气泡里写‘21！’；背景是蓝天白云，画面里还要有一句‘THE IMPOSSIBLE SKY EXPEDITION / 云上奇航’。”

判据就是逐条对：孙悟空在不在驾驶舱（✓）、飞机机身有没有那个名字（✓）、鹈鹕是不是在骑自行车（✓）、自行车是不是在飞机上（✓）、秦始皇是不是骑在北极熊上（✓）、螺丝刀和螺丝有没有（✓）、气泡里是不是 21（✓）、那句英文标题有没有（✓）。

关键点：这一题几乎不考“聪明”，考的是**一次把八件事都记住**。元素一多，模型常见的失败是“丢件”——画了鹈鹕忘了秦始皇，或者把“骑北极熊”画成“站在旁边”。所以它特别适合当“长指令稳定性”的指标。

办法不是问它“你是谁”（它会照系统提示词回答），而是让它做一件它自己控制不了的事——“随机”报数。

具体三道题：让它从 1 到 355 里挑 294 个整数，要求每个位置独立选择、不许从 1 开始数、不许递增递减、不许用等差循环。三道题分别用中文、英文、日文（或韩文）出，避免它靠“题型记忆”作答。

为什么要这么设计：大模型不是真随机数发生器，它的“随机”是从训练分布里采出来的，于是每个模型都有自己的偏好——某些数字出现得特别多、某些区段被系统性回避。把三次输出画成直方图，形状就是这只模型的“口音”。同一家的不同代际、甚至同一模型的不同量化版本，形状都可能不一样。

能干什么：识别是不是被换了模型、是不是套壳、是不是被降智。这正好接上 E2 的中转站风险——上一页说“便宜模型冒充贵模型，很难证明”，这一页就是“怎么证”的一种办法。

边界必须讲：一，它只能把范围缩小到“家族”，证不了具体版本；二，结果依赖采样温度，温度设成 0 就没意义了；三，样本要够（一次 294 个数），太短的输出统计不出来；四，这只是间接证据，不能当合同依据。

附带一句社区观察（原帖里的）：有人发现走第三方客户端时，推理 token 经常卡在 516，而直连官方的同一道题能正常思考——这被当作“被截断”的旁证，但官方从未承认。讲的时候要标清这是“社区观察”，不是结论。
                                                                                                                                                  

                                                                                                                                                  102　E2  中转站与代理池：多出来的那一层
                                                                                                                                                  来源：CLIProxyAPI、magpie 文档；OpenAI、Anthropic 使用政策；本稿整理（2026-10-18）

这一页是 E2 的总图，先把两个词分开：中转站和代理池。

共同点只有一句：请求不再直连厂商，而是先到一台中间服务器。区别在于这台服务器是谁的、它手里有什么。

中转站，是别人的服务器。你从它那儿买“额度”，它拿自己的 Key 或自己注册的号去连厂商。对你来说只有一个地址和一个 Key；对厂商来说，请求来自它，不来自你。所以数据、密钥、模型真伪、条款、资金这五件事，全都落在它身上——这就是下一页要展开的风险。

代理池，是自己的服务器。上面挂的是你自己的账号登录态或自己的 Key，网关按剩余额度、按重置时间挑一个发出去。它解决的是“一个人一份订阅不够用”，不解决“没有订阅也能用”。

画图的时候指一下两条链路：上面那条多一个方框，方框不在你手里；下面那条也多一个方框，但方框在你自己的机器上。同样是“多一层”，风险完全不同。
                                                                                                                                                    

                                                                                                                                                    103　E2b  中转站的风险：五件事都不在你手里
                                                                                                                                                    来源：OpenAI、Anthropic 使用政策；lm.ikale.io 文档；L 站中转纠纷帖；本稿整理

上一页画了链路，这一页讲代价。五条都按“它怎么发生 → 你怎么发现”来讲。

数据：输入、附件、输出都要过对方服务器。它有没有留、留多久、会不会被拿去训练，你看不到日志，也拿不到承诺。

密钥：交出 Key 就等于交出计费权。更常见的是“共享 Key”——几十个人用同一个 Key，哪天上游被封，你跟着一起停，而且账单上写的是别人的名字。

模型：一句“我是 Opus”证明不了任何事。便宜的号池里常见小模型冒充大模型，要靠固定题目＋随机数指纹来验，而这本身就说明你没法直接信。

条款：绕地区限制、共享 Key、多号刷额度，都是明确的停用理由；一旦停用，预充的钱通常不退款。

资金：预充值、无发票、跑路。这一条最容易验证：问一句“能不能开票”，大部分中转站就答不上来。

最后落到自查三问，让对方自己回答：Base URL 是谁的域名、Key 是谁开的、账单抬头是谁。
                                                                                                                                                      

                                                                                                                                                      104　E2c  代理池：一份订阅，几个人排队

账号池解决一个很具体的问题：订阅按“一个人用”卖，额度按 5 小时和每周滚动，白天用完了晚上就没了。把几个账号放进同一个网关，就能一直有额度。

四步：登录、收口、调度、计量。最容易忽略的是第一步——凭据是文件或钥匙串里的东西，复制走等于账号被复制走，改密码是唯一能收回的办法。

                                                                                                                                                              108　E3  安全护栏：四道闸，各拦各的
                                                                                                                                                              来源：OpenAI、Anthropic 使用政策；OWASP LLM Top 10；本稿整理（2026-10-18）

这一页是后面几页的地基。很多人把“模型拒绝了我”当成一件事，其实是四件不同的事。

第一层，训练侧。对齐训练让模型在概率上不愿意往某些方向走。是倾向，不是能力：换个说法、换个语言、放进一个长文档里，常常还能问出来。

第二层，系统提示词。客户端在你看不见的地方预先写了一段“岗位说明”。改一行字就可能松动，所以只能当默认值，不能当安全边界。

第三层，运行时。审批门、工具权限、文件与网络白名单。它拦的不是文字，是后果：能让模型想清楚了也动不了手。四层里只有这一层是硬的。

第四层，输出侧。分类器、敏感词、水印、日志。拦的是“落地”，拦不住已经发生的工具调用。

结论那句是重点：分不清是哪一层在拦，就会得出错误结论。
                                                                                                                                                                

                                                                                                                                                                109　E3b  破限的两条路：改话术，还是改外壳
                                                                                                                                                                来源：github.com/YuJunZhiXue/dsh-purge；OWASP LLM Top 10；本稿整理（2026-10-18）
来源索引 ›

                                                                                                                                                                  讲解与会后阅读

“破限”是个被用混的词，它至少指两种完全不同的操作，区别在攻哪一层。

第一种，提示词破限，也叫越狱。攻第 1、2 层：拒答倾向和系统提示词。手法是说服——角色扮演、分步诱导、编码绕行、把要求藏进长文档、伪造“我在做安全审计”。特点是极不稳定：同一句今天行明天不行，模型换代或加个分类器就失效。

第二种，harness 破限，攻第 3 层。它不动模型，动的是包着模型的那层壳：默认文案、审批策略、沙箱范围、工具上限。dsh-purge 是这一类里做得比较完整的——本机 @deepseek-ai 包里改掉这些，再写一段 prompt-inject.md 作为会话覆盖段。

可以点一下它的工程克制：改前把每个文件备份成 .dshpurge.bak，可 revert、可卸载；prompt-inject.md 是用户文件，还原时保留；重复应用是幂等的。

两者叠起来，就是社区说的“全解锁”：外壳放开手脚，提示词放开嘴。但这一页真正想说的是最后一行——它改变的是“谁能说不”，不改变“它到底会不会”。
                                                                                                                                                                  

                                                                                                                                                                  110　E3c  破限之后：多出来的能力，和它的账单

这一页要拆掉一个很常见的误解：很多人把“去广告”“内购免费”“模型破限”当成同一件事，叫同一个词。它们其实在三层，风险也落在不同的人身上。

第一层，内容边界，这才是严格意义上的破限。撬开的是模型愿不愿意说。能撬开一部分，但越敏感越容易编——拒答和准确性经常一起掉。

第二层，广告和内购，这是客户端的事，和模型无关。能改的多是本地展示：开屏、横幅、会员角标、功能开关。真正扣钱和发权益在服务端，客户端改出来的只是“看起来是会员”。下一頁给三个真实例子。

第三层，权限与审批，是 Agent 时代的新问题。dsh-purge 这类工具确实能把审批门和沙箱放开，让它自己删文件、付款、外发。技术上做得到，问题是：它改的是“谁能喊停”。一次误操作就是真损失，而日志里写着是你放的。
                                                                                                                                                                    

                                                                                                                                                                    111　E3d  L 站三类“成果”：代价落在谁身上

这一页用三个真实例子，把上一页的三层落到地上。名字都打了码，这不是含糊，是这类分享的通行做法：说清楚“改了什么”，不指路“去哪下”。

第一个，**模拟器。社区里流传的是“绿色版、去广告、无限多开”。改的其实是宿主 App 自己的展示层和多开限制——广告位换掉、多开校验跳过。代价：官方一升级就失效，而且多开挂机属异常行为，账号本身可能被判定。

第二个，*果视频。常见两种：去广告版、解锁会员版。能改的是本地展示——开屏、贴片、会员角标；真正发权益、扣钱在服务端。所以“解锁会员”多半只是界面变成会员，看不了会员专享。改包必须重签名，签名一变，支付、推送、微信登录全部失效。

第三个，**造价软件。这类是授权与加密锁，典型做法是本地校验绕过。如果锁只在本地校验，绕过就能跑；一旦变成联网校验、云端定额库、按账号发授权，本地补丁就没用了。而且单位里用盗版授权，是合规问题，不是技术问题。

讲的时候不要演示任何一步。这一页的价值是让人分清：技术上行得通，不等于拿得出手。

四步循环：猜（前向计算）→ 量（损失函数）→ 求方向（梯度）→ 挪一小步（梯度下降）。

这一页是正文 RAG 页（P46–47）的补充：用一张图说清“靠什么找”。

两个理由：
一，省 token，省一个量级。100 页中文资料约 5–8 万 token，整包塞进去问一次付一次；检索只把命中的 3–5 段（一两千 token）送进去，差 20–50 倍。
二，少编。材料不在眼前，模型不会说“没有”，会按“最像”往下续；原文片段摆在眼前，它有东西可抄、能标出处，再加一句“只依据片段回答”，编造率明显下降。

下半页的图是重点，讲三句：
① 每段资料和每个问题都被压成一串数字（向量），可以画在平面上；
② 意思越近，点越近——问“防撞设施”，也能落到写着“挡块”的那段上，这是关键词搜索做不到的（字面一个词都不重合）；
③ 但“近”不等于“对”。近邻里常有看着像、其实不是同一个东西的段落，所以工程上还要再做一次精排（rerank），并且必须给页码让人回原文核。

这就是“搜索”：不是查字典，是找意思最近的那几段。

边界：检索没找到，它照样会编。所以“找不到就说找不到”要写进规则，也要抽查。

                                                                                                                                                                                          122　F5  注意力怎么算：每个词带着“问题”去和其他词“对暗号”
                                                                                                                                                                                          来源：Vaswani 等《Attention Is All You Need》（2017）；权重为示意
                                                                                                                                                                                          • https://arxiv.org/abs/1706.03762
                                                                                                                                                                                          原稿备注与补充口径
                                                                                                                                                                                          讲解与会后阅读

注意力机制（简化讲法）

每个词会生成三样东西：Query（我想找什么）、Key（我能提供什么的标签）、Value（我真正携带的内容）。
1. 打分：拿“它”的 Query 去和每个词的 Key 做匹配，越相关分越高。
2. 换算比例：用 softmax 把分数变成加起来等于 100% 的权重。
3. 加权求和：按权重把各个词的 Value 混合起来，得到“它”在这句话里的新含义。

右边的热力图：每一行是“正在读的词”，每一列是“被参考的词”，颜色越深权重越大（数字为示意）。

多头注意力：同一层里有很多组独立的 Q/K/V（“头”），各自关注不同关系，比如一个头看指代（它→清单），一个头看修饰（放→一起），一个头看数字和单位。最后把各头结果拼起来。

和前后内容的联系：
- 注意力的计算量随长度平方增长，所以上下文越长越贵、越慢；
- 权重总和固定为 100%，内容越多，每份分到的越少——这就是上下文腐烂的直观原因。

来源：Vaswani et al., Attention Is All You Need, 2017, https://arxiv.org/abs/1706.03762

这一页补一个前面没讲的东西：模型的内部结构。听众常听到 MoE、稀疏、稠密、激活参数这些词，但很少有人说清它们到底差在哪、对使用者有什么影响。

一，稠密（Dense）。最直白的结构：每生成一个 token，整个网络的所有参数都要算一遍。好处是行为可预测、同一输入结果稳定；坏处是参数越多越贵、越慢——想更聪明就得付出线性增长的成本。多数“小模型”和早期模型都是稠密结构。

二，MoE（Mixture of Experts，混合专家）。把前馈层拆成很多个“专家”，每个 token 只被路由到其中少数几个（常见是 2 个），其余不参与计算。于是出现两个参数口径：总参数（所有专家加起来）和激活参数（这次真正算到的）。比如 770B 总参数 / 49B 激活，意思是“知识容量按 770B 存，但每次只动 49B”。这就是“又快又便宜又有大模型知识”的来源。

三，稀疏（Sparse）。严格说 MoE 就是一种条件计算/稀疏激活；工程上还会用稀疏注意力（只让每个 token 关注部分位置）等手段降低长文的计算量。所以说“稀疏模型”时，要问清是“参数稀疏（MoE）”还是“注意力稀疏”。

四，注意力的两个演进方向：MLA（多头潜在注意力）把 KV 缓存压小，长文更省显存；线性注意力/混合线性注意力把注意力的计算从随长度平方增长压到接近线性，代价是可能损失一部分精确回忆能力。Kimi 的 Kimi Delta Attention 属于这一类。

五，对使用者意味着什么：
· 总参数大 ≠ 一定更聪明：很多“大”是存在硬盘里的容量，不是每次都用上；
· 激活参数小 = 更快更便宜，但极难任务上可能不如稠密大模型稳；
· 稠密模型行为更可预测，适合需要复现的实验；
· MoE 的专家路由可能带来“同一问题两次答案差异更大”的现象，做基准测试要注意。

六，对部署的影响：MoE 的总参数决定显存占用（要装得下所有专家），激活参数决定算力开销。所以“770B 总参数能在单机上跑”这种说法，要看显存是否够装全部专家。

一句话收尾：架构决定的是“成本曲线”，不是“聪明程度”；聪明程度还是看评测和你自己的任务。
