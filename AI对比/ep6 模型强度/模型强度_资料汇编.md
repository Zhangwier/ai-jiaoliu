# 模型强度档位（low / medium / high / max）资料汇编

> 状态：**只整理，不进 PPT**（对应 2026-10-22 用户指令「再搜集一个模型强度 比如low high max等的影响啊区别啊什么的也是整理好」）。
> 采集日期：2026-10-22。所有数字均标注来源；只见过二级来源的标「转述」，没回原文的标「待核」，两者都不进 PPT。
> 配套文件：`引用台账.md`（逐条给链接与核验状态）、`README.md`（目录说明与未完成项）。
> 术语：本文把"每问一次模型、模型内部先想多久"的那个旋钮统一叫**强度档位**。十家叫法各不相同：Anthropic `output_config.effort`、OpenAI `reasoning.effort`、Google `thinking_level`（2.5 及以前为 `thinking_budget`）、xAI `reasoning_effort`、DeepSeek `reasoning_effort`（+`thinking.type`）、智谱 `reasoning_effort`（+`thinking.type`）、阿里百炼 `thinking_budget` / 千问 `reasoning_effort`、Kimi `reasoning_effort`、MiniMax `reasoning.effort`（仅 M3.1-Flash 有）、腾讯混元 `reasoning_effort`（+`thinking.type`，档位逐模型不同）。

## 零、先给结论（五句话）

1. **档位不是"聪明程度"，是"肯花多少 token 在思考上"**。Google 原文直说思考过程按 token 计费（"You are billed for tokens generated during the thinking process"）；Anthropic 原文说它影响**全部输出**，包括工具调用与函数参数，不只是思考段。所以档位同时改三样东西：思考长度、工具调用次数、答案的展开程度。
2. **档位是天花板，不是旋钮**。2026-05 的论文用操纵检查证明：effort 参数"sets an upper budget on generation rather than driving real-time allocation"，分配策略在训练时就定型了（arXiv:2605.16938）。人话：**调高档位不等于模型会更聪明地想，只是允许它想得更久；难题它未必真用掉预算，简单题它照样空转。**
3. **档位的收益完全取决于任务形状，不是模型属性**。OpenAI 自己发的 gpt-oss model card 里，同一套档位参数在 19 个评测上跑出三种形状：Tau-Bench Retail 单调升（35.0 → 47.3 → 54.8）、Tau-Bench Airline **中档最高**（32.0 → 42.6 → 38.0）、HealthBench Consensus **两尺寸都单调降**（84.9 → 83.0 → 82.6）。一套参数，三个方向。
4. **"降档"的代价不在知识量，在执行纪律**。Anthropic 原话：低档位"more likely to skip a search, stop early, or skip a check"；Fu et al. 实测低档安全识别失败率 72.7%，失败原因是**没识别出意图**，不是过度拒答。所以降档不是"让它变笨"，是"让它偷懒"——对付偷懒的办法是给清单，不是给提示词。
5. **档位会变，而且不会通知你**。2026 年 2–4 月 Claude Code 的默认档位被从 high 调到 medium，同时上线自适应分配、并停止回传思考内容，三处变更零 release notes。有人用 6,852 个会话日志反向审计出来：编辑前读文件的比例从 6.6 掉到 2.0，"最简单的修法"出现率涨 133%，提前收工/甩锅话术从 0 次变 173 次。**"今天它变笨了"这个体感，很可能就是档位被调了。**
6. **"档位"在用户界面上根本不是同一个控件**。九个产品九个样：ChatGPT 是滑杆六档、Claude 是模型/effort/thinking 三个独立菜单、Gemini 是"模型→思考等级→Deep Think"三层、Grok 只有 API、**豆包只有一个开关没有档位**。而且拨到某些格子上换的是**模型**不是档位（ChatGPT 的 Pro 档、豆包 1.5 的深度思考、Gemini 应用的 Pro/思考型）。**所以"我用了某模型的高档"这句话，在很多产品上没法成立。**

## 速查页 · 四档到底差在哪（low / medium / high / max，一页看完）

这张表是全文的压缩版。**每一格都能在下文找到出处**；"实测锚点"列只放已核的一手数字。

| | **low（含 none / minimal）** | **medium** | **high** | **max（含 xhigh）** |
|---|---|---|---|---|
| **官方一句话定位** | OpenAI：语音/检索/分类等"不需要推理的延迟敏感任务"；Google MINIMAL："Uses the fewest possible tokens for thinking" | OpenAI：**"Default configuration for most workloads, and a well-balanced point on the pareto curve"**；Anthropic Opus 4.7："The drop-in for the average workflow" | Anthropic Opus 4.7：**"often the best balance of quality and token efficiency"**；Google："formal code verification, or multi-turn tool execution" | Anthropic："**Reserve for frontier problems**"；OpenAI："only use when your evals show a clear benefit" |

| **相对成本（量级）** | 1× | 约 1.6×（GPT-6.1 Sol $0.13 → $0.21） | 约 2.5×（$0.32） | 约 5.5×（$0.72）；Claude Sonnet 5.5 在 max 档每任务约 19.3 万输出 token |

| **能不能关掉思考** | 只有部分模型能（DeepSeek `none`、百炼 `enable_thinking=false`、2.5 Flash `budget=0`） | — | — | **多数新旗舰不给关**（Grok / Kimi K3 / GLM-5.3 / Opus 5.5 / MiniMax M3.1-Flash） |

**三句话读法：**

1. **low → medium 是唯一"闭眼也划算"的一步**：GPT-6.1 Sol 上 **+6 分只多 $0.08**；gpt-oss-20b 在 AIME2025 上 **+35.0 点**。这一步几乎没有代价。
2. **medium → high 要挑任务**：数学题继续涨（+19.6），但 agent 与结构化输出开始出现回落（Tau-Bench Airline 42.6 → 38.0、HealthBench Hard 12.9 → 10.8）。
3. **high → max 基本是"给前沿难题付溢价"**：GPT-6.1 Sol 上 **+1 分换 +$0.33**，是第一步单位收益的约 25 倍贵。厂商自己写的是"先证明值得"。

六件从这张表立刻能看出来的事：

1. **档位名不通用**。同样是 "high"，在 Anthropic 里是中高档，在 DeepSeek 里是默认档，在 Kimi 里是**最低档**（它默认 max），在混元的 GLM-5.2 上干脆不存在。跨厂商比"我都开 high"没有任何意义。
2. **默认值不能想当然**。Gemini 同代模型里既有默认 HIGH 也有默认 MINIMAL；百炼部署的 kimi-k2.6 默认**关**思考，月之暗面自己部署的同名模型默认**开**；同一个 GLM-5.2 在智谱自己那是 max，在混元 TokenHub 上也是 max，但支持的档位集合不同。同一个模型换个部署方，默认行为就能反了。
3. **"能不能关思考"是产品决定，不是技术限制**。Grok、Kimi K3、GLM 5.3、Claude Opus 5.5 / Fable 5 / Mythos 5、MiniMax M3.1-Flash 都不给关；Gemini 2.5 Pro 不给关；OpenAI 最新两代把 `none` 也砍了。趋势是**高档模型干脆取消"不思考"选项** —— 思考不再是可选项，只是深度可调。
4. **同一个字段名可能指完全不同的东西**。xAI 的 `grok-4.20-multi-agent` 里 `reasoning.effort` 控制的是**几个 agent 协作（4 或 16）**，不是思考深度。看到字段名相同就以为语义相同，是最容易踩的坑。
5. **"传了不报错"和"传了生效"是两回事**。xAI 在不支持 xhigh 的模型上**静默降为 high**；DeepSeek 把 7 个请求值**静默归一化**成 3 档（medium→high、xhigh→high、ultra→max）；MiniMax M2.x 收到 disabled **直接忽略**。三种不同的"吞掉"，全都不报错。
6. **同一家平台内部，档位也不统一**。腾讯混元 / TokenHub 上六个模型的档位集合各不相同：Hy4 只有 high / none 两档，Hy3 是 low / high / none，DeepSeek-V4 与 GLM-5.3 与 Kimi K3 都是 low / high / max，GLM-5.2 有 max…none 全套。**同一个"档位"按钮，点开之后能选的东西取决于你在哪个模型上点。**

## 二、默认值到底怎么定的（逐模型硬证据）

### 2.1 Gemini：默认值逐模型一张表（官方文档，2026-10-21 更新）

| 模型 | 支持的档位 | 默认 |
|---|---|---|
| Gemini 3.5 Flash-Lite | 四档 | **MINIMAL** |
| Gemini 3.1 Flash-Lite | 四档 | **MINIMAL** |
| Gemini 3.1 Flash-Lite Image / 3.1 Flash Image | 仅 MINIMAL / HIGH | MINIMAL |
| Gemini 3 Pro Image | **仅 HIGH** | HIGH |
| Gemini 4 Argon Cyber Permissive | LOW / MEDIUM / HIGH | **HIGH** |
| Gemini 3.1 Pro (preview) | LOW / MEDIUM / HIGH | **HIGH** |
| Gemini 3 Flash | 四档 | **HIGH** |
| Gemini 4 Argon | LOW / MEDIUM / HIGH | MEDIUM |
| Gemini 3.8 Flash / 3.8 Flash Cyber / 3.7 Flash / 3.6 Flash / 3.5 Flash | 四档 | MEDIUM |
| Nano Banana 2.1 | MINIMAL / MEDIUM / HIGH | MEDIUM |

规律：**旗舰和 Pro 默认往高走（HIGH），轻量 Flash-Lite 默认往低走（MINIMAL），中间档默认 MEDIUM**。"默认值"本身就是厂商对"这模型该用在哪"的表态。

### 2.2 Gemini 的 MINIMAL 有两个专属坑

- **多轮对话必须带 thought signatures**，否则 `400: INVALID_ARGUMENT`。省思考的代价是必须把"思考痕迹"原样传回。
- **Gemini 4 全系不支持 MINIMAL**。上一代能用的最低档，下一代直接没有 —— 这是"档位跨代不可沿用"的实锤。

### 2.3 阿里百炼：默认开关逐模型不同

- Qwen3.8 / 3.7 / 3.6 / 3.5 系列：默认**开**思考。
- Qwen3 Plus / Flash 系列：默认**不开启**。
- 百炼部署的 kimi-k2.6 / k2.5：默认**关**；月之暗面自己部署的同名模型：默认**开**。

### 2.4 为什么这一节对本项目最重要

ep1 那十个配置，名字里就带着档位："hy4 preview 1M **high** workbuddy"、"gpt 6.1 sol **high** codex"。即：**过去几集的所有对比结果，档位是混着来的** —— 有的配置走了客户端默认，有的显式写了 high，其余八个的档位根本没记录。要下"某模型比另一模型强"的结论，前提是档位可比；而档位默认值因模型、因客户端、因部署方而异。这条前提从来没被验证过。

更狠的一刀见 3.4（Kraishan 2026）：**请求里写的档位和实际烧掉的 token 可以严重脱钩**——GPT-5.1 三档实测 116 / 118 / 118 token。也就是说，**连"配置名里写了 high"都证明不了它真的 high**。

## 三、官方自己怎么说：低档会怎样、高档会怎样

这一节全部是厂商文档原话，可直接引用。

### 3.1 Anthropic

- 关于档位本质：**"Effort is a behavioral signal, not a strict token budget."** 低档位遇到足够难的题**仍然会思考**，只是比高档位少。
- 关于高档位（`max`，Opus 4.7 段落）：**"Reserve for frontier problems. On most workloads `max` adds significant cost for relatively small quality gains, and on some structured-output or less intelligence-sensitive tasks it can lead to overthinking."** —— 官方点名**过度思考**。
- 关于低档位的**具体失效方式**（Haiku 5.5 段落）：**"In long agent prompts, the model is more likely to skip a search, stop early, or skip a check at `low`."** 三件事：跳过检索、提前收工、跳过检查。
- 关于低档位的**正面价值**（Opus 4.7 段落）：**"At lower effort levels, the model scopes its work to what was asked rather than doing more than requested."** —— 低档位反而更守范围，不做多余的事。这是"降档提质"的官方依据。
- 遇到浅思考怎么修：**"If you observe shallow reasoning on complex problems with Claude Opus 4.7, raise effort rather than prompting around it."** —— 别提提示词，先升档。
- 怎么降档：**"step down to `medium` or `low` ... once your evals show quality holds"** —— 先有 eval，再降档。
- 逐档定位（Opus 4.7 表格）：medium = **"The drop-in for the average workflow"**；high = **"often the best balance of quality and token efficiency"**；xhigh = **"recommended starting point for coding and agentic work"**。

### 3.2 OpenAI 六档定位

- **none**：语音、快速检索、分类这类不需要推理的延迟敏感任务。
- **low**：工具调用、规划、搜索、多步决策，控速度与成本（数据分析、执行型编码、客服）。
- **medium**：质量与可靠性要紧的规划、复杂推理、判断；**"Default configuration for most workloads, and a well-balanced point on the pareto curve"**（agentic 编码、研究、表格与幻灯片、长周期委派）。
- **high**：难推理、复杂调试、深度规划（agentic 编码、长周期研究、知识工作）。
- **xhigh**：深度研究、异步、长跑 agent；**"Only use when your evals show a clear benefit that justifies the extra latency and cost"**（安全与代码审查、企业生产力）。
- **max**：最复杂的题；**"If you are currently using `xhigh`, evaluate if `max` results in stronger performance"**。

OpenAI 给 xhigh / max 的条件都是"**先证明值得**"，给 medium 的定位是"大多数负载的默认、帕累托曲线上的平衡点"。厂商从没说过"越高越好"。

### 3.3 Google 四档定位

- **MINIMAL**：**"Uses the fewest possible tokens for thinking. Best for straightforward tasks that do not require extended reasoning."**
- **LOW**：**"fewer thinking tokens for faster responses. Best for high-throughput applications with low task complexity."**
- **MEDIUM**：**"Balances reasoning quality and latency. Suitable for tasks with moderate complexity"**
- **HIGH**：**"Uses the maximum thinking capacity. Best for complex prompts requiring deep reasoning, multi-step problem solving, formal code verification, or multi-turn tool execution."**

Google 的 HIGH 里出现"**formal code verification**（形式化代码验证）"和"**multi-turn tool execution**（多轮工具调用）"—— 与 OpenAI 把 agentic coding 放 high/xhigh 一致：**高档位真正的主场是长链工具调用和可验证难题**。

### 3.4 xAI 四档定位

- low：**"Latency-sensitive agentic use and simple tool calling"**
- medium：**"Complex data analysis and long-context reasoning"**
- high（默认）：**"Very challenging problems, complex math, multi-step logic, competition-level tasks"**
- xhigh：**"Maximum reasoning depth, with correspondingly higher latency"**（仅 grok-4.6 及以后；grok-4.5 传 xhigh 会被静默当作 high）

### 3.5 DeepSeek：档位映射表（静默归一化）

| 你传的 | 实际生效 |
|---|---|
| minimal | low |
| low | low |
| **medium** | **high** |
| high | high |
| **xhigh** | **high** |
| max | max |
| ultra | max |

两个后果：① 你以为在测"medium vs high 的差别"，其实两次跑的是同一档；② 厂商之间"同一档位"的比较天然失真 —— Claude 的 medium 和 DeepSeek 的 medium 落在完全不同的位置。

智谱 GLM-5.2 有类似映射：low/medium → high，xhigh → max，`none`/`minimal` → 不思考。

### 3.6 一个值得单独讲的分布：只有一家给了"低档会怎样"的原话

把十家的官方文档按"有没有说低档/高档的失效方式"排一遍，结果是：

| 厂商 | 说了低档失效方式吗 | 说了高档失效方式吗 | 有"重新校准/别沿用"提示吗 |
|---|---|---|---|
| **Anthropic** | **有**（"skip a search, stop early, or skip a check"） | **有**（"can lead to overthinking"） | **有**（Sonnet 5.5 "Its levels are recalibrated… Run a fresh effort sweep"；Opus 5/5.5 同类） |
| OpenAI | 无 | **半有**（xhigh "Only use when your evals show a clear benefit"） | 无（只有 reasoning 不跨模型族复用："does not carry between the GPT-5.6 and GPT-5.5 families"） |
| Google | 无（只有 minimal "does not guarantee that thinking is off"） | **半有**（high "may take significantly longer to reach a first (non thinking) output token"） | 无 |
| 其余七家 | **均未披露** | **均未披露** | **均未披露** |

**读法：厂商在"调高档"这件事上普遍只做正面宣传，只有 Anthropic 明确写了低档会偷懒、高档会过度思考。** 而剩下七家的文档里，你找不到任何一句"这档可能更差"。

这不是说别的厂商的档位没问题，而是**用户没有任何官方文本可以据此判断该用哪档** —— 只能靠自己的 eval。而绝大多数用户不会做 eval。**这就是"默认值决定一切"的结构性原因：官方不给你判断依据，你只能接受默认。**

## 四、机制：档位到底动了什么（五层，逐层有证据）

### 4.1 第一层：它是思考 token 的预算上限

- Google 原文：思考 token 计入账单（"You are billed for tokens generated during the thinking process"）。
- Anthropic 原文：思考 token 按 output 计费，且**计入 `max_tokens`**；`display=omitted` 只是不传回来（"Omitting reduces latency, not cost"）——**钱照收**。
- OpenAI 原文：思考 token 不可见但**占上下文**、按 output 计费；起步建议给 reasoning 预留**至少 25,000 token**，否则可能 `status=incomplete`、`reason=max_output_tokens`，出现"付了钱没看到字"。

### 4.2 第二层：它可能压根没改"怎么想"，只改了"想多久的上限"

arXiv:2605.16938（Hu & Wang，2026-05-16）在 GPT-OSS-20B 与 GPT-OSS-120B 上，跨三档 effort × 六个推理任务做操纵检查：

> "A manipulation check reveals that the effort parameter sets an upper budget on generation rather than driving real-time allocation, suggesting that the allocation policy is crystallized at training time."

标题就是结论：**Effort as Ceiling, Not Dial（是天花板，不是旋钮）**。within-task 与 cross-task 对齐度**不随 effort 变化**，贝叶斯因子偏向零假设。

这比 Anthropic 的 "behavioral signal, not a strict token budget" 更狠：**模型内部"该在哪儿多花力气"的策略是训练时定死的，推理期调档位改不了它**。这解释了后面所有"高档位不涨分甚至掉分"—— 不是模型变笨，是它把多给的预算用在了训练时学会的、与本题无关的地方。

### 4.3 第三层：档位请求值 ≠ 实际花费（最实用的方法论警告）

arXiv:2610.10049（Kraishan，2026-10-07）跑 12,350 次调用，7 个模型，0/1k/4k/8k 四档思考上限，两个发现：

1. **偏差不随思考预算下降**：加倍思考预算，社会偏见不降反微升（Claude +0.0029/倍，p=.372；**GPT-5.1 β=+0.0084，p=.018**，显著）。
2. **"请求档位"是坏代理**：GPT-5.1 三档实测思考 token 分别是 **116 / 118 / 118** —— 数值上几乎没有区别。另有 DeepSeek-R1 **79%**、Qwen3 **52%** 的调用**超出**上限。

**本项目的直接后果**：ep1 配置名里的 "high" 是一个**请求值**，不是实测值。要证明档位可比，必须回看响应里的 `reasoning_tokens` / `reasoning_content` 长度。这一条要写进口径文档。

### 4.4 第四层：过度思考是可测量的浪费（三个递进的指标）

- **Chen et al.**（arXiv:2412.21187，ICML 2025 poster #45540）："2+3=?" 类问题思考 token **暴涨 1,953%**；**>92%** 的题在**首轮思考里就给出了正确答案**，而首轮只占 **<60%** 的 token；最简难度（Lv.1）的 outcome efficiency **<50%**。摘要原话："excessive computational resources are allocated for simple problems with minimal benefit"；机制是"repeatedly generate redundant homogeneous solutions"。
- **Zhai et al.**（arXiv:2605.23926，2026-04-21）：把它升级成可测的 ρ —— 步骤冗余度 **61%–93%**；**8 个条件里 6 个**的 median critical prefix 只有 **1 步**（即第一步就把方向定死了）；即使在 MATH-500 最难的 Lv5 上，冗余仍达 **46%–85%**。结论：冗余是"只看结果、不看长度的奖励"的结构性产物，不是难度导致的。
- **Guan et al.**（arXiv:2610.13570，2026-10-09，中科院信工所）：给出 OR（overthinking ratio）与 AD（accuracy drop）双指标，6 模型 × 4 benchmark：平均 **OR = 64.3%**，**满额思考的平均分比"最优截断点"低 9.03 个百分点**；OR 分布 41.1–74.4%，AD 分布 5.64–13.40 pp，GPQA 上 AD 最高 **16.98 pp**。

**Guan 的一个反直觉发现必须单独标出**：OR 与 AD 的 Spearman 相关只有 **−0.330**。即"想得多"和"掉分多"是**两件事**——MATH 上 OR 78.8% 但 AD 只有 1.83pp；GPQA 上 OR 61.4% 却 AD 16.98pp。**不能用"它想太久了"直接推断"它答错了"。**

### 4.5 第五层：test-time compute 要分层分配，不是一把给满

Snell et al.《Scaling LLM Test-Time Compute Optimally can be More Effective than Scaling Model Parameters》arXiv:2408.03314（ICLR 2025，OpenReview 4FWAwZtd2n，被引 2000+），PaLM 2-S*，MATH 按难度分 5 个 bin：

- compute-optimal 策略达 **>4×** 效率（16 次采样的最优策略追平 64 次朴素采样）；FLOPs 匹配下**打赢 14× 大的模型**。
- **按难度分流**：易题（bin 1–2）走 sequential revision；中难题走 PRM 搜索；最难题（bin 5）原文说"no method makes much meaningful progress"，此时该加的是预训练算力，不是思考预算。
- **易题上 beam search 随预算增大反而掉分**（PRM 过优化）；naïve revision 有 **38%** 的改动是"把对的改错"。

这是后来所有"高档负收益"观测的理论源头：**预算不是钱，是配额；给错了地方就是负收益。**

### 4.6 补充层：档位改行为，不只改正确率

- Anthropic 的 "skip a search, stop early, skip a check" —— **低档首先伤的是执行纪律**。
- Fu et al.（arXiv:2602.08874，2026-02-09）gpt-oss 三档 × 1,200 例安全任务：低档 safe rate **仅 7%**，失败构成里 **Harm-ID-Failure 占 72.7%** —— 即**没识别出有害意图**，不是过度拒答。低→中 safe rate **27.0% → 64.6%**，中→高 **64.6% → 80.4%**（思考长度翻倍以上）。
- Zhao et al.（arXiv:2509.06861，v3 2026-08-06，NUS）反向一刀：14 模型 × 3 个知识密集集，o4-mini 思考 token 涨 **>8×** 而准确率**持平**；幻觉率 GPT-5-mini **+15%**、gpt-oss-20b **+25%**；gpt-oss-20b 新增幻觉里 **95.0%** 来自"低档时压根没尝试"的题 —— 即**高档让它敢答原本不敢答的题，于是编得更多**。

**这两篇合起来是"档位的双刃"最干净的一手证据**：低档省下的思考会变成"漏识别"，高档多给的思考会变成"多编造"。中间那段才是安全区。

> "We train the models to support three reasoning levels: low, medium, and high. **These levels are configured in the system prompt by inserting keywords such as "Reasoning: low".** Increasing the reasoning level will cause the model's average CoT length to increase."

> "We generally see **log-linear returns** on most tasks, where longer CoTs provide higher accuracy at a relatively large increase in final response latency and cost. **We recommend that users pick a model size and corresponding reasoning level that balances these tradeoffs for their use case.**"

> "our gpt-oss-20b use **over 20k CoT tokens per problem on average for AIME**."

这三句合起来给了三件事：① **档位在这套模型里是靠系统提示词里的一句话实现的**（不是采样参数）；② 官方自述是"对数线性回报"，不是"越高越好"；③ 官方推荐的动作是"**按你的用例去平衡模型尺寸与档位**"——把模型尺寸和档位并列成两个可互换的杠杆。

⚠️ 另一处矛盾值得单列（跨厂商对比的好素材）：
- **gpt-oss model card**："in multi-turn conversations the reasoning traces from past assistant turns **should be removed**."
- **DeepSeek 官方**：带 tools 时**必须把历史 `reasoning_content` 全量传回**，否则 400。

**同一件事（历史思考痕迹要不要回传），两家给了完全相反的硬要求。** 这说明"思考痕迹"在上下文里怎么处理，目前没有行业共识，各家自成一套。

### 5.2 Agent / 工具调用类：中档最优 + 高档 logic drift

Yang et al.（arXiv:2603.07915，2026-03-09）gpt-oss-20b 三档：

| 评测 | low | medium | high |
|---|---|---|---|
| Tau-Bench Retail | 35.0 | 47.3 | **54.8** |
| Tau-Bench Airline | 32.0 | **42.0** | 38.0 |
| BrowseComp-Plus | 8.00 | 34.0 | **42.7** |

该文把高档在 Airline 上的掉分归因为 **logic drift（逻辑漂移）**：想得越久，越容易在中途偏离原有约束。全 high → 全 low 整体掉 **近 20%** —— 即"一律开 low"是灾难，"一律开 high"只是次优。

### 5.3 代码：中档最好，高档过度工程

Digital Applied《Reasoning Effort: Cost vs Quality Benchmarks 2026》（2026-04-23）5 个前沿模型 × 3 档 × 900 次任务（每格 3 次多数投票）。Expert-SWE refactor：

| 模型 | low | medium | high |
|---|---|---|---|
| GPT-5.5 Pro | 58.7% | **73.1%** | 71.4% |
| Claude Opus 4.7 | 54.1% | 68.4% | **69.8%** |

GPT-5.5 Pro 的 high **比 medium 低 1.7 点**。归因具体：**23% 的高档位运行出现过度工程** —— 跨无关模块改名、引入测试不需要的抽象、破坏集成测试依赖的类型签名。

同一批数据里 AIME 2026 通过率（low→high +18~22 点，全文最大档位收益）：

| 模型 | low | medium | high |
|---|---|---|---|
| GPT-5.5 Pro | 69.3% | 79.3% | **91.7%** |
| Claude Opus 4.7 | — | 75.4% | **89.1%** |
| Gemini 3 Pro DT | — | 72.8% | **87.4%** |
| DeepSeek V4 | — | 70.9% | **84.2%** |
| Grok 4.5 | — | — | **81.4%** |

报告金句（可直接当章节标题）：

> "Math reasoning is where the dial pays its rent. Code reasoning is where the dial is misused."
> "Most teams default every workflow to high reasoning out of caution and pay 4-12× over the right tier."

### 5.4 代码 agent 的另一条更狠的证据

Cuadron et al.（arXiv:2502.08235，Berkeley / CMU）在 **SWE-bench Verified 4,018 条轨迹**上：**只挑 overthinking 得分低的解**（即同一模型多次采样，按"啰嗦程度"挑），性能 **提升近 30%**、成本 **下降 43%**。

这条的意思是：**在 agent 任务上，"少想"不是妥协，是提升。** 而且它不需要改模型、不需要调参 —— 只是换选哪个解。

### 5.5 知识密集 / web 研究：高档净负

- FutureSearch《Higher effort settings in LLMs can reduce accuracy》（Deep Research Bench，150+ 真实网络研究任务）：

| 模型 | low | medium | high |
|---|---|---|---|
| Claude 4.5 Opus | 54.9% / $0.31 / 413s | — | 54.8% / $0.46 / 375s |
| Claude 4.6 Opus | 53.1% / $0.24 / 159s | — | 55.0% / $0.55 / 461s |
| Claude 4.6 Sonnet | 50.4% / $0.27 | — | **54.9%** / $0.46 |
| Gemini 3 Flash | **49.9%** / $0.05 / 390s | — | 47.9% / $0.14 / 631s |
| GPT-5 | **49.6%** / $0.25 / 526s | 48.6% / $0.35 / 469s | 48.1% / $0.39 / 582s |

GPT-5 **严格单调下降**；五个模型里三个高档等于或更差；Claude 4.5 高档分数持平而**成本 +47%**。成本涨幅（同一批任务）：GPT-5 **+56%**、Claude 4.5 Opus **+48%**、Claude 4.6 Sonnet **+70%**、Gemini 3 Flash **2.8×**。唯一"涨分"的是 Claude 4.6 Sonnet（50.4% → 54.9%），代价是 **+70%** 成本。

归因：研究类任务瓶颈在**取信息**不在**想得深**，多给的预算被用来"怀疑已有好结论、追越来越边缘的来源、把简单答案过度限定"。

⚠️ **计时口径警告**：FutureSearch 有两篇（`effort-paradox` 2026-02-12、`effort-scaling` 2026-02-18），两篇的延迟测量方法不同（naive wall-clock → 每步均值 ×（步数+1）），**延迟数字不能跨篇比较**，分数与成本可以。上表秒数为同一篇内部口径。

- Zhao et al. 给出同构的分界：**information-limited 任务**（需要外部检索）加搜索能从 41.2% 提到 53.0%；**不带搜索时 20× 思考 token 毫无收益**。**杠杆是检索次数，不是档位。**

- Gema et al.（arXiv:2507.14417，TMLR 2025-12）从"逆缩放"角度补了一刀：4 类任务上**推理越长系统性越差**；Claude Sonnet 4 随推理变长出现更多 **self-preservation（自我保全）** 表述。即长思考会放大模型已有的坏模式，而不是创造好的。

### 5.6 成本与延迟：三个轴一起涨

- 单题成本：GPT-5.5 Pro low $0.31 → high $0.78（约 **2.5×**）；报告另一处口径写思考溢价达 **17×**（指 token 消耗量，非单价）。
- 跨模型性价比：按"每个正确答案的成本"，DeepSeek V4 high $0.04 vs GPT-5.5 Pro high $0.78，差 **19×**。
- 首 token 延迟（TTFT P50）：低档 **0.4–1.5s**、中档 **4–12s**、高档 **18–90s**（Claude Opus 4.7 带 extended thinking：low 0.8s → high 28s）。
- **缓存轴（最易忽略）**：Kimi 官方明确写"切换档位会导致 prefix-cache 命中失效，建议在会话开始前就定好档位，不要在同一会话中切换"；Anthropic 相反，提供 mid-conversation 改档 beta（header `mid-conversation-output-config-2026-07-01`），**per-message 改保留 prompt cache，改顶层默认值会让 cache 重算**。同一动作两家行为相反，成本差几倍。

### 5.7 一条会被模型换代冲掉的经验

OpenAI 讲 GPT-6 Astra 时写：它 **"achieved stronger results using substantially fewer output tokens"**，且 **"Its estimated API cost per task was lower than earlier models despite its higher per-token pricing"**。

**"每 token 单价"和"每次任务成本"是两条不同的轴。** 更贵的新模型可能更省钱，因为它想得更短。所以"开 high 更贵"这个直觉，长期看被换代冲掉 —— 换代的收益大于调档位。

### 5.8 五档完整扫描：边际收益衰减到什么程度（Artificial Analysis，经 DataNorth 转述）

这是唯一一份**同一模型五档全跑、同时给分数和单任务成本**的数据。GPT-6.1 Sol（读于 2026-10-08，Intelligence Index 由 10 个评测合成，覆盖 agentic 编码到长上下文推理）：

| 档位 | Intelligence Index | 单任务成本 | 相对上一档 |
|---|---|---|---|
| low | 42 | $0.13 | — |
| medium | 48 | $0.21 | **+6 分，+$0.08** |
| high | 50 | $0.32 | +2 分，+$0.11 |
| xhigh | 51 | $0.39 | +1 分，+$0.07 |
| max | 52 | $0.72 | **+1 分，+$0.33** |

**读法：low→medium 是六分换八分钱；xhigh→max 是一分换三十三分钱。** 最后一档的单位收益是第一步的 **约 25 倍贵**。medium→max 三档加起来只涨 4 分，成本却翻了 3 倍多。

同一份数据还给出一条反直觉的速度事实：**高档位不是"打字更慢"，是"打得更多"** —— GPT-6.1 Sol 五档的输出速度都稳定在 **49–56 token/s**，几乎不变。所以高档位带来的等待时间，**全部来自多生成的那些 token**，不是推理引擎变慢。

配套的两个数字：

- **Claude Sonnet 5.5 在 max 档每任务约用 193,000 输出 token**，是 GPT-6 Astra 在自身 max 档的**约 7 倍**。同一档位名，两家的绝对思考量差 7 倍 —— 再次证明"都开 max"不能横向比。
- Qwen：qwen3.7-plus 上**推理占输出 token 的 60% 以上**，关掉思考后总延迟降 **60–75%**。

### 5.9 Reasoning Dial：目前唯一"预注册 + 可复现"的档位基准

Kaggle 预注册基准，60 题 × 4 模型 × 4 档 × 2 次重复，**1,800+ 次调用**，代码与数据公开（[github.com/Abeera81/reasoning-dial](https://github.com/Abeera81/reasoning-dial)）。这是本文引用的一堆数字里，**唯一一个别人能原样重跑一遍的**。

- **12 个"模型 × 任务"组合里，7 个准确率无变化**，而每个正确答案的成本涨 **1.5–3.4×**。
- 唯一统计显著的提升：**gpt-5.4-mini 在逻辑题上 15% → 97.5%**。
- 输出 token 倍数（同一题、最高档 vs 最低档）：**gpt-5.4-mini 14.08×**、gpt-oss-120b 4.60×、gemini-3.7-flash 2.24×、claude-haiku-5.5 1.99×。

**读法：档位对"小模型 + 逻辑题"是救命，对"大模型 + 已有能力覆盖的题"是纯加价。** 14 倍 token 换不来分数的组合，比换来分数的组合多得多。

| GPT-6.1 Sol | 7.72 / 42.4s | 7.96 / 41.3s | **8.61 / 207.0s** |
| Claude Opus 5.5 | — / 27.9s | **7.89** / 57.1s | 7.86 / 66.7s |
| Gemini 3.8 Flash | 7.74 / 52.5s | 7.96 / 259.9s | **8.30 / 213.8s** |

**这张表给出两个直接反例：**

**它与本项目 ep1 的关系（这段最该被讲）**：ep1 的鹈鹕测法是"同一句提示词、十个配置、一次生成"，缺的正是"同一配置的档位维度"。**这份榜单把那一维补上了，而且用的是同一句提示词。** 所以 ep1 那句"某模型画得更好"的成立范围，现在可以说得更准：**在各自客户端默认档位下、且档位这一维未被单独扫过。**

## 六、三个必须知道的陷阱

### 6.1 陷阱一：档位跨代不可沿用

- Anthropic（Opus 5.5）：**"Run an effort sweep on your own evals rather than carrying settings over from an earlier model."**
- Anthropic（Sonnet 5.5）：**"Its levels are recalibrated, so a level doesn't produce the same amount of thinking as the same level on Claude Sonnet 5."**
- Google：Gemini 4 系列**直接不支持** MINIMAL —— 上一代的最低档，下一代不存在。

**名字一样，刻度一样不了。** 在 4.5 上调好的 high，到 5.5 上可能等价于原来的 medium，也可能等价于 xhigh。

### 6.2 陷阱二：档位与"关思考"是两个独立开关，混用会 400

- Claude：effort 管总量、thinking 管开不开。`xhigh`/`max` 下不能关（400）；Opus 5.5 任何档位都不能关（400）。
- OpenAI：`none` 就是关；但 GPT-6 Astra 不支持 `none`（400），GPT-6.1 Sol 连 `none` 与 `minimal` 都不支持。
- Gemini：MINIMAL 在多轮里必须带 thought signatures，否则 `400 INVALID_ARGUMENT`。
- DeepSeek：思考模式带 `tools` 时**必须把历史 `reasoning_content` 全量传回**（含没发生工具调用的轮次），否则 **400**。
- 智谱：GLM-5.3 / 5.3-FLASH 传 `thinking.type=disabled` **直接报错**。

**共同规律：越想省事地把档位调到最低，越容易撞上"必须回传思考痕迹"的硬要求。**

### 6.3 陷阱三：档位会被别的参数静默吞掉

- DeepSeek 思考模式下 `temperature`、`presence_penalty`、`frequency_penalty` **不生效**，官方明说为了兼容"**will not trigger an error but will also have no effect**"—— 不报错，就是没用。`top_p` 亦分模型：deepseek-flash 思考模式仅 0.95–1.0 有效（低于 0.95 按 0.95 算），deepseek-v4-pro 有 tools 时固定 0.95。
- xAI：`presencePenalty`、`frequencyPenalty`、`stop` 与推理模型同用**直接报错**。

对本项目的意义：**ep1–ep5 里如果有过"换个温度再试一次"的操作，在某些模型的思考模式下等于什么都没做。**

这一层最容易被忽略，但对本项目最重要 —— 因为 ep1–ep5 的十个配置全是在**客户端**里跑的，用户看到的从来不是 `output_config.effort`，而是模型选择器里的一个词。

### 7.1 九家客户端档位对照

ep1–ep5 的十个配置全是在客户端里跑的，用户看到的从来不是 `output_config.effort`，而是模型选择器里的一个词。下面九行里，**前四行的客户端叫法来自 DataNorth 2026-10-12 二次整理（转述），后五行是本轮直接抓官方文档核的**。

**这张表最该被记住的一行是豆包：它根本没有档位。** 九个产品里，两个只有开关（豆包、智谱清言），四个是"开关 + 若干档"（DeepSeek / 千问 / Kimi / Grok 只有档没有开关），只有 Claude 与 ChatGPT 把模型、档位、思考拆成三个独立控件。**"模型强度"这个词在用户界面上的形态，九家九个样。**

### 7.1b 按一下按钮，换的是档位还是换模型？

这是本节最有价值的一个区分，因为它决定"同一模型横评"能不能成立：

- **同模型换档（官方明说）**：Claude —— 官方原话是"thinking 与 effort 是两个独立设置"；OpenAI —— "pro 模式与推理强度也是两个独立设置"。
- **换模型**：豆包 1.5 的"深度思考"背后是**另一个模型**；Gemini 应用里选 Pro / 思考型是**换模型**，**Deep Think 才是再往上一层的档位**。
- **焊死在一起**：ChatGPT 的 Pro 档（见 7.2）。
- **其余厂商未披露**。

→ 所以"我用了 X 模型的高档"这句话，在豆包上可能根本不成立（它没有档），在 Gemini 应用上要先分清你换的是模型还是档位，在 ChatGPT 上最后一格干脆换了模型。

### 7.1c 同一模型按付费分层（这条最容易被忽略）

- **ChatGPT**：官方原文 **"Some paid plans omit Astra Extra High"**；**Free / Go 只给 GPT-6 Luna**。
- **Gemini**：**Deep Think 仅 Google AI Ultra 订阅可用。**
- **Claude**：官方提示**提高 effort 会更快撞到用量上限** —— 档位不是免费的，它烧的是你的配额。

→ 对本项目的直接含义：**ep1–ep5 十个人用的是不同账号、不同套餐。** 就算两个人选的模型名一模一样，档位也可能因为套餐不同而不同。这一层以前从来没被记进口径文档。

### 7.2 最关键的一个发现：ChatGPT 最高那档是换模型，不是换档位

DataNorth 转述 OpenAI 帮助中心（help.openai.com/en/articles/20001354）的内容：

> **"GPT-6 Sol powers the first four levels and Pro uses GPT-6 Pro, which is powered by GPT-6 Astra."**

即：ChatGPT 的 Instant / Medium / High / Extra High 四档背后是同一个 GPT-6 Sol，只是 effort 不同；但 **Pro 那一档直接换成了 GPT-6 Astra**。

这条把"档位"和"模型"两件事在同一个 UI 里焊死了 —— **用户以为自己只是在拨一个滑块，其实拨到最后一格时，模型也换人了。** 而按 3.2 的官方定位，Astra 是"用更少 token 拿到更强结果、单任务成本更低"的那类模型，与"多想想"是相反的方向。

同一段还给出了各套餐的档位权限：**Plus 只有 Instant / Medium / High，Extra High 与 Pro 要 Pro / Business / Enterprise**；Free 与 Go 只有一个 Think 选项，跑 GPT-5.6 Luna。并且 —— **"On Plus and Pro, Instant no longer moves up a level by itself when a question turns out to be complex, so pick the level yourself."**（以前会自动升级档位，现在不自动了。）

**这一句就是本 ep 的核心命题的官方注脚：档位正在从"系统自动判断"变成"用户自己选"，选错就自己承担。**

### 7.3 ChatGPT 各档背后跑的是什么

- Instant / Medium / High / Extra High → **GPT-6 Sol**（effort 递增）
- Pro → **GPT-6 Pro**，底层是 **GPT-6 Astra**
- Free / Go 的 Think → **GPT-5.6 Luna**

⚠️ 全部标「转述」（DataNorth 二次整理，OpenAI 帮助中心原文本轮抓取返回 422）。进 PPT 前需回到 help.openai.com 原文核一遍。

### 7.4 用户能看到的另一个反直觉事实：打字说"想仔细点"没用

DataNorth 明确写：**"In ChatGPT it does not: OpenAI states that typing 'think harder' or 'think deeply' does not switch the thinking level, so select the level in the model picker."**

而 Anthropic 给的是另一条路：**当延迟原因必须保持低档时，在提示词里加一句"这个任务涉及多步推理"**。

**两家在"能不能用提示词换档位"上给了相反的答案** —— 一家说没用，一家说这是低档位的补偿手段。这一条对"给 AI 加一句'仔细想想'"这个全民习惯是直接打击。

## 八、一个正在发生的活案例：Claude Code 的档位被悄悄调低（2026-02 至 04）

这是全篇最贴近本项目的一手事件 —— 不是实验室，是真实生产环境，而且有人把它量化了。

### 8.1 事件

AMD AI Director **Stella Laurenzo** 在 GitHub issue [anthropics/claude-code#42796](https://github.com/anthropics/claude-code/issues/42796)（2026-04-02 开，Anthropic 24 小时内 close 为 completed）里，用**自己机器上的 6,852 个 Claude Code session JSONL、17,871 个 thinking block、234,760 次 tool 调用**做了反向审计。HN 讨论冲到 1,147 分、630+ 评论，The Register 2026-04-06 跟进报道。

### 8.2 三件事同时发生（按时间）

1. **2026-02-09**：Claude Opus 4.6 上线 **adaptive thinking** —— 让模型自己决定每个 turn 想多久。
2. **2026-03-03**：**默认 reasoning 强度从 high 调到 medium**。
3. **2026-03-05 起**：灰度推 `redact-thinking-2026-02-12` header，让 thinking 内容默认不回传到本地 transcript（Mar 5 1.5% → Mar 8 58.4% → Mar 12+ 100%）。

**没有一条出现在 release notes 里。** Claude Code 团队负责人 Boris Cherny 在 issue 下的回应确认了这三点，并承认 adaptive thinking 在**某些 turn 上把推理预算分配到了零**。

### 8.3 量化结果（这是最该被引用的部分）

- **思考深度**：thinking block 的 `signature` 字段与思考内容长度有 **0.971 的 Pearson 相关**（7,146 组配对样本）。据此估算，中位思考量从 1 月底的 ~2,200 字符降到 3 月的 ~600 字符，**−73%**；而且 2 月下旬就已降 ~67%，**早于** redaction 上线。
- **行为变了，输出质量跟着变**（`Read:Edit` = 每次编辑前读几个文件）：
  | 时期 | Read:Edit | 未经阅读直接编辑的占比 |
  |---|---|---|
  | 好（1/30–2/12） | **6.6** | 6.2% |
  | 过渡（2/13–3/7） | 2.8 | 24.2% |
  | 退化（3/8–3/23） | **2.0** | **33.7%** |
- **整文件重写比例翻倍**：Write 占全部修改 4.9% → 10.0% → 11.1%（从"精准改一行"退化成"整篇重写"）。
- **自我纠错循环**（"oh wait / actually / let me reconsider"）：每千次工具调用 8.2 → 15.9 → **21.0** → 26.6，翻三倍多。
- **"simplest" 一词出现率**：每千次工具调用 2.7 → 4.7 → 6.3（**+133%**）—— 模型开始系统性选"最省事"而不是"最正确"。
- **提前收工 / 请示许可 / 甩锅**：团队写了一个 `stop-phrase-guard.sh` 钩子拦截这类话术，**3 月 8 日前 0 次触发，之后 17 天触发 173 次**（甩锅 73、请示许可 40、提前收工 18、贴"已知限制"标签 14、拿会话太长当借口 4）。最狠的一天 43 次，约每 20 分钟一次。
- **用户打断率**：每千次工具调用 0.9 → 1.9 → 5.9 → **11.4**（涨 12 倍）。
- **成本反噬**：2 月用户提问 5,608 次、3 月 5,701 次（人的投入几乎没变），但 3 月 API 请求 119,341 次（2 月 1,498，**80×**）、输出 token 62.6M（**64×**）、按 Bedrock 价折算 **$42,121**，而实际订阅只付 $400。**降档省下的算力，被返工十倍百倍地吐回去。**

### 8.4 为什么这个案例必须进本 ep

它同时证实了前面所有章节的论断：

| 本文前面的论断 | 这个案例的对应证据 |
|---|---|
| 档位主要伤害**执行纪律**，不是知识量（3.1 Anthropic 原话 "skip a search, stop early, skip a check"） | Read:Edit 6.6 → 2.0；1/3 的编辑发生在没读过的文件上 |
| 降档 = 模型选"最省事"而非"最正确" | "simplest" 出现率 +133%；整文件重写翻倍 |
| 自适应思考会把预算分到零 | Boris 亲口承认；`CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING=1` 是官方给的解法 |
| 请求档位 ≠ 实际档位（4.3 Kraishan） | 团队早就在用 `effort=max`，**照样退化** —— 因为真正的旋钮是 adaptive 分配，不是 effort 上限 |
| 档位变化对用户不可见（本节） | 三处变更，零 release notes；redaction 让用户连"它想了多久"都看不见了 |
| 缓存与 mid-conversation 改档（5.6） | 团队被迫每次新会话手动 `/effort max` |

### 8.5 这个案例给出的两条可用做法（可直接抄）

1. **`CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING=1`** —— 禁用自适应思考，强制每 turn 用固定推理预算。因为问题最严重的场景恰恰是"某些 turn 被分配到 0"。
2. **`/effort max`（会话级）** —— 把上限从 medium 抬回 max。

**两个必须一起做**：Stella 采集数据时**已经是 effort=max**，问题照样存在 —— 说明单抬上限不管用，还得禁掉上限以下的随机分配。这是"上限"与"分配"是两个独立旋钮的实证。

而且注意一个结构性事实：**这已经是 Anthropic 过去八个月里至少第五次面对同类指控**（2025-08/09 三个 infra bug 影响约 30% Claude Code 用户；2025-12 一个月五起 incident；2026-01 底 harness rollback；2026-04 这次）。每一次都真实存在，每一次承认都落后社区抱怨数周到数月。

### 8.6 一条经济学解释（对讲稿很有用）

Stella 的算法很朴素：按 3 月真实用量、用 Bedrock on-demand 价折算，**$42,121/月**；她实付 **$400/月**，**122 倍**。

结论不是"厂商坏"，是**订阅制的经济学决定了 runtime 层的默认值一定会被往下调**：全速 reasoning 在算力上太贵，固定月费盖不住。于是厂商只剩一个不透明、不需要发公告的旋钮 —— 默认档位。Boris 说会"测试给 Teams 和 Enterprise 用户默认 effort=high"，这正是把这个矛盾产品化的动作：**把全速 reasoning 重新包装成更贵的付费档，同一款工具里不同用户拿到不同的 runtime 默认值。**

这条规律不专属于 Anthropic —— Cursor 2025 年中的 credit-based 计费与 auto mode、OpenAI 用 reasoning effort 切档，撞的是同一面墙。

## 九、与本项目 ep1–ep5 的关系（本文最该被讲的部分）

### 9.1 过去五集的"档位变量"从来没被锁过

`核对/鹈鹕配置映射.json` 十个配置，至少两个把档位写进了名字（E = hy4 preview 1M high workbuddy，G = gpt 6.1 sol high codex），其余八个走客户端默认且档位未记录。这意味着：

- ep1（识图）：十个配置的差异里**混着"模型能力"与"档位"两个自变量**。
- ep3（做表，七轮沙箱迭代）：迭代中若换过模型/客户端，档位很可能同时被动改变。
- **要下"某模型比某模型强"的结论，必须先证明两边档位可比。这条前提目前没有证据。**

这不是推翻前面的结论，是给结论加边界：**"在各自客户端默认档位下"。**

### 9.2 更狠的一层：写在名字里的 high 也可能是假的

Kraishan 2026（arXiv:2610.10049）实测 GPT-5.1 三档思考 token 116 / 118 / 118 —— **请求值三个样，实际花费几乎一样**。所以"配置名里写了 high"连"它真的 high 了"都证明不了。

**要证明档位可比，唯一办法是回看响应里的 `reasoning_tokens`（Google / 百炼）或 `reasoning_content` 的长度（DeepSeek / xAI）。** 这是一条要写进 `核对/模型对比口径v3.md` 的硬要求。

### 9.3 "降智"体感 vs 档位：两件事，用户分不出来

成品46 里 P65（B1c 降智）讲的是 Anthropic 2025-08/09 三个 bug，最严重时 16% 的 Sonnet 4 请求受影响 —— 那是**同档位下的基础设施故障**。P99–P101（E1 降智测试四道题）测的是**同档位下质量是否掉了**。

本 ep 讲的是**档位本身被改动**。两者体感完全一样（"今天它变笨了"），成因完全不同：

| | 降智（E1 已覆盖） | 档位（本 ep） |
|---|---|---|
| 触发 | 服务端 bug / 负载 / 路由 | 参数被调低，或默认值随换代变化 |
| 模型 | 同一个 | 同一个 |
| 档位 | 不变 | 变了 |
| 可自查 | 看状态页、看社区是否集体反馈 | 看请求参数、看响应里实际思考 token |

**两者叠加就是"今天特别笨"**：模型默认档位从 high 改成 medium（换代重标定），再赶上一次服务端故障。

### 9.4 温度 0 跑 1000 次得 80 种回答（P12）与档位的关系

P12 的结论是"温度 0 也不确定"。加上 6.3：**在思考模式下，温度这类采样参数可能被静默忽略**。所以"温度 0 为什么还不确定"在推理模型上有一个更朴素的可能答案：**你设的温度压根没生效，真正在变的是思考长度和思考路径。**

（推断，需实测：同一 prompt、同一模型，思考开/关 × 温度 0/1 四格，看方差来源。列入待办。）

### 9.5 对口径文档的具体改动建议

`核对/模型对比口径v3.md` 用 K1/K2/K3 三个检查点、分母 3。这套口径不受档位影响，但**可复现性受影响**。建议加两列：

1. **请求档位**：当时真正发出去的值（不是配置名里的字）。
2. **实测思考量**：`reasoning_tokens` 或 `reasoning_content` 字符数。

有这两列，"两边档位可比"才是一句能被检验的话，而不是一句保证。

## 十、可操作清单（能直接照做的）

1. **先定质量线，再倒推档位。** 官方口径一致：先跑 eval，证明"降档后质量还在"，再降（Anthropic："once your evals show quality holds"；OpenAI xhigh 段："Only use when your evals show a clear benefit"）。**不要从"我觉得 high 更稳"开始。**
2. **按任务形状定档，不按"重要程度"定档。** 数学、可验证逻辑、形式化检查、长链工具调用 → 高档真赚；代码重构、结构化输出、受限格式 → **中档常常最优**；检索/研究类 → 档位几乎无关，**该加的是检索次数和来源质量**；安全/意图识别类 → 中档起步（低档漏识别 72.7%，高档多编造 +25%）。
3. **默认选 medium 是有数据支撑的。** 三家厂商的一手材料指向同一处：gpt-oss 官方表里 Airline / HealthBench Hard 都在 medium 见顶；Anthropic 说 medium 是"帕累托平衡点"；OpenAI 说 medium 是"大多数负载的默认"。
4. **eval 与生产必须同档。** 拿 high 调出来的提示词，投产切 medium 会直接崩（Anthropic 明说低档会 skip a search / stop early / skip a check）。
5. **低档位必须配显式清单。** 既然低档的失效方式是"漏步骤"，就把它漏的步骤写成硬检查项（本项目现成例子：`hc_check` 式门禁、ep3 的七轮检查表）。**降档不是降低要求，是把要求外化成清单。**
6. **高档位要给足 `max_tokens`。** OpenAI 建议 reasoning 预留 ≥25,000 token，否则 `status=incomplete` + `reason=max_output_tokens`，钱花了字没出。
7. **注意缓存。** 同一会话换档位：Kimi 会废掉 prefix cache；Claude 的 per-message 改档能保住 cache，但改顶层默认值不行。**长会话定好档位再开工。**
8. **跨代必须重扫。** 换模型代际时跑一次档位扫描（至少 low / medium / high × 一小组 eval），不要沿用旧配置。
9. **记录实际生效值。** 日志里要写请求真正发出去的值 + 响应里实际思考 token 数。两者都可能和你想的不一样（Kraishan 实测 116/118/118）。
10. **agent 任务可以"少想 + 挑解"。** Cuadron 那条（SWE-bench 4,018 轨迹，挑低 overthinking 的解 → 性能 +30%、成本 −43%）说明：不改模型、不改参数，只改"选哪个解"，就能同时省成本涨质量。
11. **先确认这个产品有没有档位。** 豆包只有开关、Grok 只有 API、智谱清言是 App 开关。**在没有档位的产品上讨论"开 high"是无效的**；在 ChatGPT 上拨到最后一格，换的是模型（Astra）不是档位。
12. **把套餐差异记进口径。** ChatGPT 的 Extra High 与 Pro 要 Pro / Business / Enterprise，Free / Go 只有 Luna；Gemini 的 Deep Think 仅 AI Ultra 可用。**同一句"我用了 high"，不同账号可能根本不是同一个东西。**
13. **优先信"可复现"的数字。** Reasoning Dial（1,800+ 次调用、代码公开）说 12 个组合里 7 个准确率无变化、成本涨 1.5–3.4×；这个结论比任何商业博客都硬，因为它能被重跑。

## 十一、讲稿可用的一句话

**主推（有事件、有数字、有反转）：**

> **"AI 的'深度思考'不是一个开关，是一笔预算。这笔预算怎么花，训练的时候就定死了，你调它只是给了个天花板 —— 这就是为什么数学题上它真管用（AIME 从 50 分涨到 92 分），代码重构上它反而害事（高档比中档低 1.7 个点），查资料上它基本没用（GPT-5 越高分越低）。厂商文档里没有一句说'越高越好'，全是'先证明值得'。OpenAI 自己发的评测表就写着：Tau-Bench Airline 低中高是 32.0 / 42.6 / 38.0。"**

**如果要打"这件事已经发生在你身上"：**

> **"今年 2 月到 4 月，Claude Code 的默认档位被从 high 悄悄调到了 medium，没人发公告。有人拿自己 6,852 个会话日志做了反向审计：模型改代码前先读文件的比例，从每次编辑读 6.6 个文件掉到 2.0；三分之一 的编辑发生在它根本没读过的文件上；它开始频繁说'最简单的修法'——这个词的出现率涨了 133%；它开始提前收工、甩锅、问'要我继续吗'，一个专门拦这些话的脚本，之前 17 天触发 0 次，之后 17 天触发 173 次。而 3 月的 API 请求量是 2 月的 80 倍，折算成账单是每月四万二千美元，他实付四百。"**

**最短版（一句话钉住概念）：**

> **"档位不是让它更聪明，是让它想得更久 —— 而想得久只对'能验证的难题'有用。"**

**如果要打"这玩意儿连界面都不统一"：**

> **"同样叫'深度思考'，ChatGPT 是一个六档滑杆，Claude 是模型加 effort 加 thinking 三个独立菜单，Gemini 是三层菜单，Grok 干脆只有 API，豆包只有一个开关 —— 它连档位都没有。更要紧的是：ChatGPT 拨到最后一格，换的不是档位，是模型。所以'我用了某模型的高档'这句话，在好几个产品上根本不成立。"**

**给"那我该选哪档"的落点：**

> **"默认用 medium。low 到 medium 是六分换八分钱，xhigh 到 max 是一分换三十三分钱。厂商自己都这么建议。"**
